# Архитектурные решения

Этапы 1–2 · 2 октября 2026 года. Архитектурные решения выбраны; репозиторий и shell из ADR-012 уже созданы. Station-процессы, БД, транзакционный Runtime и product features остаются предстоящей реализацией. Изменения решений оформляются новыми записями с причиной; аудит этапа 0 не переписывается.

Основная спецификация: [ARCHITECTURE.md](ARCHITECTURE.md). Форматы взаимодействия: [CONTRACTS.md](CONTRACTS.md). Проверка решений: [ACCEPTANCE.md](ACCEPTANCE.md).

## ADR-001. Один владелец состояния станции

Контекст: несколько диспетчеров и ticks могут одновременно затронуть один блок. Независимый state внутри нескольких API workers расходится.

Решение: один Station Runtime на stationId, ограниченная очередь, один поток обработки изменений, process ownership guard и транзакционные блокировки. API читает неизменяемые committed projections. Симуляция остаётся отдельным Python-пакетом, хотя запускается в процессе приложения.

Альтернативы: отдельные микросервисы блоков/стрелок/поездов потребовали бы распределённых транзакций; shared state в браузере не даёт общего владельца. Отложены. Цена решения — масштабирование записи ограничено одним Runtime; для одной demo-станции сначала измеряется этот предел. CPU-heavy solver выполняется отдельно.

## ADR-002. Текущее состояние плюс журнал и outbox

Контекст: нужно переживать сбой между сохранением маршрута и отправкой WS, а также воспроизводить историю.

Решение: current tables + events с post-values + periodic snapshots + command_results + audit + transactional outbox. Все последствия команды сохраняются одной транзакцией. Доставка at-least-once, client frames дедуплицируются. История восстанавливается без повторного вызова LLM/solver.

Альтернативы: только RAM теряет историю; публикация до commit показывает несуществующее состояние; полноценный event-sourced storage увеличивает сложность миграций и восстановления. Для прототипа он не нужен. Цена решения — нужно контролировать соответствие current projection журналу и иметь versioned replay reducer.

## ADR-003. PostgreSQL и SQLite как отдельные профили

Решение: PostgreSQL — серверный default; SQLite с WAL на локальном диске — single-PC demo. Одинаковые domain/use-case interfaces, отдельные adapters управления транзакциями и database-specific constraints. SQLite не эмулирует SELECT FOR UPDATE: write-lock получается до чтения.

Обе БД проверяются интеграционно. Уникальность занятия блока и станционный serialization gate защищают команду вместе; ORM не объявляется автоматической защитой от гонок. Нельзя использовать файл SQLite через сетевую шару или запускать два владельца одной станции.

Цена решения — две матрицы миграций и интеграционных тестов. Один общий fixture должен давать одинаковые доменные результаты. Специфичные PostgreSQL exclusion constraints могут усиливать проверку интервалов, но core-инвариант не должен зависеть только от них.

## ADR-004. Топология общая, геометрии две

Решение: одна domain-топология с directed edges, block ownership, переходами стрелок и conflict zones. 2D использует диспетчерские координаты; 3D — геометрию в метрах. Связь идёт через стабильные edgeId и offsetM, не через обмен координатами SVG.

Альтернатива: независимые маршруты и spline каждого UI-режима могут показывать физически разные движения. Отказ от неё — условие согласованности. Цена решения — валидация связности, длин, направления и границ каждого geometry asset.

Исходное изображение определяет композицию, но не реальные размеры, радиусы, уклоны и нормативы. Все отсутствующие характеристики явно принадлежат mock-профилю. Изменение топологии первого демо выполняется при RESET в новый run; редактирования графа под движущимся поездом нет.

## ADR-005. Учитывать весь состав и дистанцию остановки

Решение: поезд хранит footprint нескольких блоков и историю пройденных рёбер для хвоста. Маршрут замыкает конфликтные зоны до безопасного освобождения; сигнал определяется authority. Ускорение demo-времени увеличивает число шагов, а не допускаемую длину скачка.

Альтернатива: один currentBlock на голову недостаточен, освобождает стрелку до прохода последнего вагона. Цена решения — более сложные тесты границ и поворотов. Прототип не моделирует сцепление двух разных поездов внутри одного блока; манёвр — отдельная защищённая операция существующего состава/локомотива.

Отказ стрелки или закрытие пути под составом сохраняет occupancy и вызывает incident. Команда инцидента не переводит стрелку под поездом и не удаляет поезд. Для уже физически недостижимой остановки действует явно обозначенная пауза модели, а не скрытое мгновенное торможение.

## ADR-006. Оптимизатор предлагает, Runtime исполняет

Решение: CP-SAT и эвристика строят кандидатов с жёсткими ограничениями; LLM только объясняет. Принятый план задаёт расписание. Непосредственно исполняемые операции проходят атомарную резервацию, будущие — повторную проверку в момент исполнения.

Альтернативы: LLM как единственный планировщик не даёт проверяемой модели ограничений; предварительное замыкание всех будущих маршрутов блокирует станцию. Цена решения — нужно обрабатывать отклонение будущей операции и повторно планировать.

Baseline и alternatives сравниваются на одном horizon/config. Три допустимых варианта — свойство подготовленного demo-case. Если решения нет, UI показывает INFEASIBLE и причины; эвристика также проходит проверку допустимости. Статус OPTIMAL допустим только при соответствующем результате solver.

## ADR-007. Отдельные stateVersion и controlRevision

Решение: stateVersion отражает каждый опубликованный пакет, controlRevision — изменение условий принятия решений. Рост координат внутри блока не инвалидирует план автоматически. ACCEPT проверяет baseControlRevision, окно исполнения и текущую безопасность.

Альтернатива: сравнение только stateVersion на 10 Гц делает пользовательское принятие плана почти невозможным. Сравнение только controlRevision без текущих физических проверок пропускает устаревший тормозной расчёт. Цена решения — явный список причин увеличения controlRevision и тесты на каждую из них.

Устаревший controlRevision не принимается молча. Нужен новый расчёт и новая осознанная команда; UI показывает изменение причины. Даже одновременные ACCEPT разных планов проходят один serialization gate.

## ADR-008. Атомарные WS frames и изолированный replay

Решение: один FRAME на транзакцию, sequence внутри run, baseStateVersion, список изменений сущностей и семантических событий. Snapshot + watermark снимают гонку подключения. Транспортные heartbeat/resync не потребляют domain sequence.

Альтернативы: независимые сообщения block.occupied и train.position.updated могут показывать промежуточно невозможное состояние; смешение replay/live повреждает view при новых событиях. Цена решения — нужен transactional reducer, отдельный replay store и политика bounded queues.

Retention по умолчанию 72 wall-hours; UI replay — последние 15 simulation minutes. Старый topology/config и предшествующий snapshot удерживаются столько же, сколько зависимые события. Экспорт фиксирует cutoffSequence; выполняемому export/replay-запросу на время чтения гарантируется согласованный срез retention.

## ADR-009. Same-origin browser auth

Решение: opaque access/refresh cookie, серверные сессии, Argon2id, CSRF и Origin check, ротация и отзыв. Не требуется JWT, внешний identity provider или интернет. Роли проверяются при поступлении и исполнении команды.

Альтернатива: token в localStorage упрощает demo, но повышает риск извлечения из JS; долгоживущий stateless JWT затрудняет немедленное применение роли и logout. Цена решения — lookup сессии и координация refresh. Все server workers будущего масштабирования должны видеть одно хранилище сессий.

Исключение HTTP без Secure ограничено loopback demo. LAN/VPS/VPN используют TLS, а не переносят локальные ослабления. Открытый `/health` содержит только статусы, детальная конфигурация — ADMIN. Начальный ADMIN создаётся setup-командой, пароль в README/seed не вшивается.

## ADR-010. Offline является профилем поставки

Решение: приложение запускается из подготовленного пакета без загрузок. JS, шрифты, модели, текстуры, Swagger, runtime, wheels и данные входят в поставку. Онлайн-установка и offline-start — разные процедуры. Модель локального LLM устанавливается отдельно заранее; отсутствие модели не делает систему неработоспособной.

Альтернатива: start.bat с npm install/pip install/CDN не выполняет offline-требование. Цена решения — объём дистрибутива, lock-файлы и проверка холодного запуска на машине без кэша. Docker-профиль требует заранее доставленных images; сертификаты локального LAN не должны зависеть от интернет-проверки при каждом старте.

## ADR-011. Честные показатели эффективности и скорости

Решение: версия формулы, коэффициенты, знаменатели и окна доступны в настройках и истории. Недостаток данных отображается через coverage/WARMING_UP/NO_DATA. Предсказанный индекс не выдаётся за фактический.

Latency измеряется по отдельным участкам: событие → видимое состояние, расчёт → варианты, событие → полный новый план. Цель < 500 мс для индикации не считается выполнением требования < 500 мс для готового плана. Целевой solver budget — 3 с; приёмка фиксирует оба результата.

Цена решения — возможно, строгий критерий полного плана за 500 мс потребует дополнительной оптимизации и не будет выполнен первым solver. Это не повод скрывать время или показывать заранее выдуманные варианты. Конкретные аппаратные условия и нагрузка фиксируются в benchmark на этапе 32.

## ADR-012. Ограничить реализацию текущим этапом

Решение: этап 1 создаёт архитектуру, контракты, ADR и матрицу приёмки. Skeleton, manifests, сервер, UI, SQL и тесты поведения принадлежат следующим этапам. Проверки документации не называются проверками работающего приложения.

До этапа 2 остаются инженерные уточнения: совместимые версии библиотек и их лицензии/поставка, структура сборки Python-пакетов, инструментальные конфиги. До этапов 3/5 — точный DDL и mock-топология. До этапа 32 — измерение аппаратных пределов. Эти пункты не блокируют архитектуру и не требуют выдумывать отсутствующие исходники.
