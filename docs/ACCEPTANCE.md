## 5. Финальная демонстрация

Demo fixture содержит семь поездов из запроса: П-303 на станции, P-3001 и C-102 с запада, Г-2002, C6-4003, Г-2004 и П-304 с востока. Транспортные IDs независимы от кириллицы/латиницы отображаемых номеров. Значения длин, расписания и ресурсов помечены MOCK.

NORMAL_OPERATION запускает заранее принятый seed-план. Новые варианты после инцидентов требуют ACCEPT; это сохраняет отличие начальной работы от автоматического применения рекомендаций.

1. После входа DISPATCHER видит рабочие часы, семь поездов, занятость и параметры seed-плана.
2. START запускает движение по серверным координатам; те же составы видны в 2D и 3D.
3. Сценарий TRAIN_DELAY добавляет +9 минут выбранному подходящему поезду; видны затронутые операции.
4. TRACK_CLOSURE закрывает путь 3, создаёт инцидент и конфликт с запланированным прибытием.
5. На UI сразу видны факт и причина; job рассчитывает минимум три допустимых альтернативы для этого fixture.
6. У вариантов показаны исходный/новый план, время расчёта, задержки, изменения путей и прогноз SEI; шаблонное объяснение доступно без LLM.
7. «Показать на схеме» подсвечивает вариант, не меняя резервации.
8. ACCEPT проходит safety и текущую ревизию, фиксирует план и доступную к исполнению операцию.
9. Стрелки проходят MOVING, затем устанавливаются; сигнал разрешает движение только после выполнения условий.
10. Поезд, ещё не вошедший на закрытый путь, проходит допустимую траекторию к новому назначению; состоявшийся вход не исправляется телепортацией.
11. Индекс обновляется с видимыми факторами; audit содержит действия, actor и результаты.
12. Replay возвращает картину до инцидента и после ACCEPT без изменения live; CSV/PDF фиксируют период.
13. Повторяется burst из 10 инцидентов, отключение/подключение клиента и работа без внешнего AI; сохраняются замеры.

Эти шаги покрывают последовательность из 20 действий пользовательского demo-сценария; отдельный DEMO.md на этапе 33 даст точные кнопки и идентификаторы после появления UI.

## 6. Измерение производительности

Референсная нагрузка для первого benchmark: 10 путей, 7 поездов, >= 2 блока на путь плюс подходы/горловины, 5 браузеров, скорость x1 и x10, одиночный инцидент и burst из 10. Полные фактические CPU/RAM/OS/DB/browser/build versions фиксируются в отчёте. 3D измеряется отдельно от 2D, с указанием GPU и viewport.

| Метрика | Цель | Граница измерения |
| --- | --- | --- |
| Live publish rate | 10 Гц штатно, >= 1 Гц под demo burst | Committed telemetry frames, независимо от кадров анимации |
| Visible event latency | p95 < 500 мс; также публикуется max | Получение внешнего события / постановка сценария → render подтверждённого изменения |
| Solver alternatives | <= 3 с wall-time budget | Начало job → готовый проверенный пакет вариантов |
| Full replanning latency | Отдельно проверяется < 500 мс из Word-ТЗ | Событие → видимый полный новый план; progress indicator не считается планом |
| Reconnect | Актуальное состояние после handshake/resync | Корректность версии обязательна независимо от скорости |
| Очереди и память | Ограниченные размеры, отсутствие неограниченного роста | Slow-client, solver timeout, sustained burst |

Измерение UI latency требует сопоставимых временных шкал: browser monotonic marks + server timings и оценка RTT/clock offset. Простое вычитание Date.now двух машин не принимается. Помимо percentile сохраняются raw samples, ошибки и число исключённых прогревочных измерений. SLA полного плана < 500 мс не объявляется выполненным по solver budget 3 с; если не достигнут, это отдельный зафиксированный результат и задача оптимизации.
