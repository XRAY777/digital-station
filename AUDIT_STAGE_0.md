Для полноценного аудита существующей реализации не хватает исходников или ссылки на репозиторий, инструкции запуска, конфигурации без секретов, схемы/миграций БД и примеров API/событий. При отсутствии этих материалов план ниже описывает разработку с нуля в текущей папке.

Для готового продукта должны быть подтверждены все отсутствующие в материалах подсистемы: серверная модель, движение, safety, маршруты, ресурсы, оптимизация, realtime, авторизация, история, отчёты и эксплуатационные сценарии.

Дополнения и неоднозначности требований, которые следует явно учесть при проектировании:

- Word-ТЗ предусматривает краткосрочную историю, например 24–72 часа; пользовательский запрос требует replay минимум 15 минут. Предложение: хранить историю 72 часа с настраиваемым сроком и показывать в replay последние 15 минут по умолчанию.
- Word-ТЗ отдельно требует диаграмму движения и обработку входного потока: буферизацию, валидацию, дедубликацию, сглаживание. Их нельзя потерять за разработкой 3D.
- 3D, подробная блоковая модель, RBAC, пять способов запуска и offline-first подробно заданы пользователем; это расширение исходного Word-ТЗ.
- Требование видимого обновления плана < 500 мс и расчёта за несколько секунд нуждается в двух метриках. Предложение: < 500 мс для индикации события/конфликта/начала расчёта и отображения уже рассчитанного результата; отдельно бюджет solver в несколько секунд. Это предлагаемая трактовка для согласования, а не доказанное выполнение исходного требования о полном плане за 500 мс.
- Физические длины, ограничения скорости, матрица несовместимости стрелочных маршрутов и границы блоков не выводятся из PNG. Для демо потребуется явно помеченный mock-набор.
- Презентация на 10–12 слайдов и видео/live-демо указаны в формате сдачи Word-ТЗ. Это финальные материалы, а не работа текущего этапа.

## 6. Архитектурные проблемы

Подтверждённых дефектов кода нет: кода нет в области аудита. Нельзя назвать слишком большие файлы, дублирование, смешение UI с логикой или неправильное хранение состояния.

Есть требования, которые недостаточно реализовать буквально:

1. `currentBlock` не описывает весь состав. Поезд может занимать несколько блоков; нужно учитывать голову, хвост, длину и множество занятых блоков.
2. `status` пути не заменяет состояния блоков. Занятость, резервирование и административное закрытие лучше хранить отдельно, а сводный статус пути вычислять по явному правилу.
3. Набор соединённых рёбер графа сам по себе не задаёт разрешённые проходы через стрелку. Нужны разрешённые переходы и конфликтные зоны.
4. Зелёный сигнал требует согласованной цепочки проверок и защищённой дистанции торможения, а не одной проверки свободного следующего блока.
5. Оптимизационный план не равен уже открытому маршруту. Планируемые интервалы использования ресурсов отделяются от текущих блокировок инфраструктуры.
6. Runtime, БД и браузер не должны независимо изменять «главное» состояние. Нужен один владелец записи и восстановление после сбоя.

Это рекомендации к будущей модели, не найденные ошибки неизвестного приложения.

## 7. Проблемы безопасности

Проверить пароли, токены, CORS, CSRF, SQL injection, XSS и RBAC невозможно без приложения. Утечек секретов в коде не обнаружено, поскольку исходники не предоставлены; это не заключение о безопасности системы.

Предлагаемый минимум: Argon2id для паролей; серверная проверка ролей; короткоживущая access-сессия и ротация refresh; отзыв сессий; rate limiting входа и команд; аудит; проверка идентификаторов и схем данных. Выбор Argon2id следует [рекомендациям OWASP по хранению паролей](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Для браузерного клиента предлагаются HttpOnly-cookie, SameSite, Secure при HTTPS, CSRF-защита изменяющих запросов и проверка Origin у WebSocket. Детали cookie и жизненного цикла сессии опираются на [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). Для локального HTTP-демо нужен отдельный явный профиль; его настройки нельзя переносить в LAN/VPS-профиль.

Все пользовательские, сценарные и AI-команды проходят одинаковые правила авторизации и безопасности. LLM не получает прямой доступ к изменению станции. Права OBSERVER проверяются даже при ручном POST-запросе. Ключ идемпотентности связывается с пользователем, типом команды и хешем тела запроса; другое тело с тем же ключом отклоняется.

## 8. Проблемы realtime

Фактические проблемы канала неизвестны. На представленном фрагменте нет индикатора подключения и времени последнего обновления. Это наблюдение относится только к кадру.

Предлагаемый контракт события: `eventId`, `sequence`, `schemaVersion`, `stationId`, `simulationRunId`, `stateVersion`, `simulationTime`, `occurredAt`, `type`, `payload`.

Начальная подписка получает snapshot на определённой sequence и все последующие события без зазора. Повторы отбрасываются; пропуск sequence вызывает resync. После reconnect клиент передаёт последний идентификатор; если история уже удалена, сервер отправляет новый snapshot. RESET создаёт новый simulationRunId, поэтому счётчики предыдущего запуска не смешиваются с новым.

Heartbeat, backoff с jitter, статус соединения и возраст данных обязательны. Stale определяется по времени получения и heartbeat, а не только по часам клиента. Медленным клиентам ограничивается очередь; промежуточные координаты можно объединять, но события резервирования и безопасности терять нельзя. Сглаживание применяется к отображению и допустимой телеметрии, а не к фактам занятости блока.

## 12. Backend authoritative state

Не обнаружен в переданных файлах. Нет state endpoint, runtime, журнала команд или snapshot, по которым можно проверить владельца состояния.

Предложение: один Station Runtime сериализует команды и ticks для станции. Успешное изменение сохраняет состояние, audit и событие в одной транзакции; публикация выполняется после commit. При сбое commit состояние не продвигается. После перезапуска runtime восстанавливается из сохранённой версии и истории.

Frontend хранит только полученную проекцию, выбор объекта, настройки отображения и отдельную replay-проекцию. Оптимизатор читает snapshot и не изменяет live state.

SQLite предлагается для одного экземпляра локального демо: запись сериализуется, read-check-write выполняется в транзакции с ранним захватом write-lock и обработкой busy. PostgreSQL — основной серверный профиль, с блокировкой затронутых ресурсов в едином порядке и проверкой актуальных версий. Один Python-lock без транзакционной защиты БД недостаточен.

## 15. Optimization Engine

Не обнаружен. Показанный в карточке номер пути не доказывает наличие алгоритмического назначения.

Предлагается планирование операций на горизонте времени: необязательные интервалы для альтернативных путей, ограничение непересечения использования блоков/стрелочных зон/платформ/ресурсов, последовательность операций, технические окна, длина состава, допустимое направление и время освобождения хвостом.

Целевая функция минимизирует взвешенные задержки, простой и изменение уже принятого плана. Приоритеты и веса хранятся в конфигурации. OR-Tools предоставляет интервальное планирование и ограничения непересечения ресурсов; пример основы — [официальная задача Job Shop](https://developers.google.com/optimization/scheduling/job_shop). Железнодорожные ограничения нужно реализовать и проверить отдельно.

Расчёт выполняется в отдельном процессе с бюджетом времени, вне цикла WebSocket и симуляции. Результат содержит исходную stateVersion, runtime расчёта, статус решателя, причины и прогноз метрик. Устаревший результат нельзя применять без повторной проверки.

Для главного demo dataset должны существовать минимум три допустимых альтернативы. В общем случае система показывает столько вариантов, сколько действительно допустимо, и явно сообщает об отсутствии решения. При timeout эвристика может предложить безопасный допустимый вариант без утверждения об оптимальности. Ожидание также допустимо; нарушать ограничения ради трёх карточек нельзя.

## 16. Conflict Detection

Не подтверждён: на снимке задержки есть, но задержка сама по себе не является доказательством найденного конфликта.

Нужен отдельный модуль, который обнаруживает пересечение текущих или планируемых интервалов использования блоков, конфликтные стрелочные переходы, занятые платформы, закрытия, отказы, недостаток ресурсов, несовместимые манёвры и влияние опоздания на последующие операции.

Safety Engine запрещает опасную команду до изменения состояния. Conflict Engine описывает существующую/прогнозируемую проблему и её причины. Нельзя заменить превентивную проверку уведомлением уже после двойного занятия блока.

Повторные ticks обновляют существующий конфликт по устойчивому ключу, а не создают сотни дублей. Разрешение конфликта требует устранения причины; нажатие «закрыть уведомление» не должно разблокировать инфраструктуру.

## 17. Что сохранить

Сохранить десять нумерованных путей, ориентацию запад/восток, две платформы, зонирование парков, карточки подхода, компактные сведения о задержках, тёмную палитру и приоритет схемы над административными таблицами.

Изображение служит визуальным ориентиром. Если исходный UI будет предоставлен, сначала следует проверить и переиспользовать его подходящие компоненты и геометрию. Сейчас оценить возможность повторного использования кода нельзя.

## 18. Что переработать

Конкретные файлы на переработку не назначаются: они не доступны. В будущем интерфейсе нужны кликабельные объекты, инспекторы состояния, сигналы, блоковые границы, легенда, индикация связи, выделение предлагаемого маршрута и явное различие live/replay.

Визуальная геометрия должна ссылаться на IDs общей модели. Экранные координаты 2D и физические метры 3D — разные проекции одного графа; масштаб PNG нельзя использовать как физическую длину.

Перенос хранения состояния из браузера на backend, замена CSS-движения или рефакторинг монолитных компонентов потребуются только в том случае, если такие реализации обнаружатся в предоставленном позднее коде.

## 20. TARGET ARCHITECTURE

**Предложение: модульный сервер с единственным владельцем состояния станции, отдельными пакетами domain/simulation/optimization/AI и отдельным frontend.** Для первого демо достаточно одного процесса API/Station Runtime и отдельного процесса расчёта оптимизации. База данных — отдельная зависимость; SQLite локально не требует отдельного сервера.

Такое разделение сохраняет возможность вынести Station Runtime в отдельный сервис позднее, но не требует брокера и нескольких независимых записывающих сервисов для первой рабочей станции. В Word-ТЗ допускается встроенный аналог шины событий.

Ключевые границы:

1. **Domain:** чистые сущности, состояния, инварианты и типы команд; без React, FastAPI и ORM.
2. **Simulation:** граф, часы, движение, route/safety/conflict/resources. Единственное место применения переходов состояния.
3. **Backend application:** auth, command pipeline, транзакции, repositories, ingest, outbox, REST, WebSocket и read projections.
4. **Optimization:** неизменяемый входной snapshot, математические ограничения, альтернативы и прогноз; без записи live state.
5. **AI:** чтение структурированных результатов и объяснения. ACCEPT возвращается в общий command pipeline.
6. **Frontend:** визуализация полученных данных, интерполяция и пользовательские команды. Без собственных решений о безопасности.
7. **Database:** текущая модель, версии, события, снимки, настройки, сессии и audit.

Поток изменения: Authenticate → Authorize → Validate → Serialize → повторное чтение актуального состояния под блокировкой → Safety/Conflict → подготовка следующего состояния → транзакция State + Audit + Outbox → Commit → обновление опубликованной серверной проекции → WebSocket. В случае сбоя процесс публикации повторяет отправку outbox; клиент устраняет дубли.

Симуляционные ticks, сценарии и ручные команды используют того же владельца записи. Резервирование всего маршрута атомарно: либо все необходимые блоки и стрелки закреплены, либо ни один. Активный маршрут нельзя отменить так, чтобы освободить блоки под составом; освобождение следует модели занятия и замыкания.

Нельзя просто запускать несколько Uvicorn workers с отдельным state в каждом. Процессы обычно не разделяют память, как описано в [документации FastAPI по deployment](https://fastapi.tiangolo.com/deployment/concepts/). Поэтому предложен один Station Runtime; масштабирование API потребует выделенного владельца состояния и согласованного транспорта команд.

Offline-профиль включает собранный frontend, локальные JS/fonts/3D-assets, Python-зависимости, БД и seed. `start.bat` не должен устанавливать пакеты из интернета. Для первой установки без сети нужен заранее подготовленный пакет или сохранённые Docker images. Облачный LLM остаётся необязательным.

### Обязательные приёмочные проверки

| Тест | Ожидаемый результат |
| --- | --- |
| 1. Два поезда претендуют на один блок | Только один получает владение; в том числе при одновременных запросах |
| 2. Конфликтующие маршруты | Второй маршрут не открывается; нет частичного резервирования |
| 3. Стрелка под поездом | Перевод отклоняется, включая случай, когда голову уже прошла, а хвост ещё нет |
| 4. OBSERVER отправляет команду | Backend возвращает 403, состояние и резервации не меняются |
| 5. Закрытие пути | Конфликт и пересчёт; занятый путь не очищается искусственно |
| 6. Опоздание | Расчёт новой версии плана с влиянием на последующие операции |
| 7. Reconnect | После потери/дублирования/пропуска событий клиент получает актуальную версию |
| 8. AI пытается обойти safety | Невалидный или устаревший вариант отклоняется общим pipeline |

Дополнительно: восстановление после сбоя между commit и публикацией; отсутствие повторного эффекта команды; replay без записи в live; reset с новым run ID; недоступная БД; solver timeout; отключённый LLM; x10 на границе красного сигнала; atomicity резервирования нескольких ресурсов.
